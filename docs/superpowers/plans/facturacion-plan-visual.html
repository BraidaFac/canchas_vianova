Estrategia de encriptación del certificado

¿Cómo se protege el certificado ARCA?

Solo en env var
ENCRYPTION_KEY
(32 bytes hex)
→
Proceso en Node.js
AES-256-GCM
encrypt(cert.pem)
→
Guardado en Supabase
cert_encrypted
key_encrypted
✓ La ENCRYPTION_KEY nunca está en la DB — solo en env vars de Vercel.
✓ El certificado en texto plano solo existe en RAM durante el llamado a ARCA.
✓ El superadmin puede actualizar el cert desde la UI sin acceso al servidor.

Ciclo de vida de un comprobante

Estados posibles

⏳ pendiente ✓ emitida ✗ fallida — anulada
pendiente → emitida — ARCA responde con CAE
pendiente → fallida — error de ARCA o timeout
fallida → emitida — cron reintenta (max 3) o admin reintenta manual
fallida → emitida — admin ingresa CAE obtenido del portal ARCA
fallida / pendiente → anulada — admin decide no emitir (cancelación de reserva, etc.)

Tareas en orden

Task 1 — Base de datos
SQL Migration: tablas config_facturacion y comprobantes
Crear las dos tablas en Supabase. config_facturacion tiene fila única con id=1. comprobantes guarda cada intento con payload y respuesta completa de ARCA.
Task 2 — Librería
AES-256-GCM crypto + ENCRYPTION_KEY env var
Funciones encrypt() y decrypt() en lib/facturacion/crypto.ts. Genera y agrega ENCRYPTION_KEY de 32 bytes a .env y Vercel.
Task 3 — Librería
TypeScript types + instalar @afipsdk/afip.js
Types ConfigFacturacion, Comprobante, ComprobanteEstado. Instalar el SDK con npm.
Task 4 — Librería
Afip client + lógica core de emisión
getAfipClient() carga config desde DB y desencripta cert/key. emitirFactura() crea registro pendiente → llama ARCA → actualiza con CAE o marca fallida.
Task 5 — API
Config API (solo superadmin) + status endpoint
GET/PATCH /api/admin/config/facturacion — encripta cert/key antes de guardar, nunca los devuelve al cliente. GET /api/admin/facturacion/status — llama FEDummy de ARCA.
Task 6 — API
Comprobantes CRUD + cron worker
Lista paginada con filtros, detalle por id, reintentar, anular, registrar CAE manual. Cron worker en procesar-cola que verifica salud de ARCA antes de reintentar.
Task 7 — UI
ConfigFacturacionTab (superadmin)
Badge de estado ARCA con botón "Verificar". Formulario completo: CUIT, razón social, condición IVA, punto de venta, token SDK, modo testing/producción. Textarea para pegar cert.crt y key.pem.
Task 8 — UI
ComprobantesTab
Tabla paginada con filtro por estado. Badges por estado. Acciones: reintentar, ver detalle, anular. Dialog de detalle con JSON del payload/respuesta ARCA y campo para CAE manual.
Task 9 — UI
Página /admin/facturacion + sidebar
FacturacionClient con tabs "Comprobantes" (todos) y "Configuración" (solo superadmin). Agregar "Facturación" al AdminSidebar. Agregar cron a vercel.json.
Task 10 — API
Auto-emisión al confirmar reserva
Modificar el PATCH de reservas para que cuando estado → "confirmada", llame emitirFactura() en fire-and-forget. Si falla, el registro queda pendiente y el cron lo reintenta.
